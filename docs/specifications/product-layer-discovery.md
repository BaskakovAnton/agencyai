# Продуктовый слой: discovery (C7, решение OD-6=B)

| Поле | Значение |
|---|---|
| Статус | **ИССЛЕДОВАНИЕ — решения не приняты**, реализация не начата |
| Дата | 28.11.2026 |
| Контекст | Сейчас продукт — прототип: модель процессов и данные живут в памяти, хранение и авторизация не реализованы |
| Задача | Описать варианты продуктового слоя и требования, чтобы владелец мог выбрать направление |

## 1. Что есть сейчас (FACT)

- Данные модели: 30 обращений, 37 ситуаций, орг-модель (подразделения, сотрудники, назначения) — в `src/data` и `src/core`.
- Сборка: SPA в один `app.js`, публикуется на GitHub Pages; серверной части нет.
- Роли и права: доменные проверки (`hasPermission`, `allow/subset/conditional`) есть, пользователей и сессий нет.
- Аудит: append-only события в памяти; при перезагрузке страницы состояние теряется.
- Персональные данные: в модели обезличены (роли вместо ФИО жителей); реальных ПД нет.

## 2. Варианты

| Вариант | Суть | Плюсы | Минусы | Когда выбирать |
|---|---|---|---|---|
| A. Остаться прототипом | Ничего не добавлять, явно написать ограничения | Ноль затрат, честно | Нет практического применения | Для демонстрации регламента |
| **B. Локальный продукт (рекомендую)** | Хранение в браузере (IndexedDB) + импорт/экспорт JSON; пользователь выбирается вручную; журнал append-only на клиенте | Работает без сервера и бюджета, данные не покидают машину | Нет совместной работы и настоящей авторизации | Один оператор, пилот в приёмной |
| C. Клиент + сервер | API, БД (PostgreSQL), аутентификация, роли, аудит на сервере | Совместная работа, настоящий аудит | Нужны хостинг, эксплуатация, регламент ПД | Несколько операторов, реальные обращения |
| D. Интеграция с существующими системами | Обмен с МФЦ/ЕДДС/1С по API | Встраивается в контур | Зависит от чужих интерфейсов | Когда есть утверждённая интеграция |

## 3. Требования к любому варианту с реальными данными

| ID | Требование |
|---|---|
| R-D-1 | Разделение персональных и служебных данных; ПД жителей не попадают в демо-сборку |
| R-D-2 | Аутентификация и роли: житель, депутат-диспетчер, помощник, подрядчик, наблюдатель, аудитор |
| R-D-3 | Журнал действий append-only: изменение и удаление записей запрещены, хранится 5 лет (ФЗ-59) |
| R-D-4 | Согласие на обработку ПД и политика хранения (ФЗ-152); журнал доступа к ПД |
| R-D-5 | Резервное копирование и восстановление; проверка целостности журнала |
| R-D-6 | Экспорт обращения и отчётов в машиночитаемом виде |

## 4. Риски

| Риск | Оценка | Снижение |
|---|---|---|
| Некорректная обработка ПД | Высокий | Вариант B без реальных ПД до отдельного решения; обезличивание по умолчанию |
| Потеря данных в браузере | Средний | Экспорт/импорт JSON, напоминание о резервной копии |
| Рост объёма вне плана | Средний | Вариант B ограничен одним оператором и не требует сервера |

## 5. Открытые вопросы

1. Кто пользователи пилота и сколько их одновременно?
2. Есть ли требование хранить ПД в защищённом контуре организации?
3. Нужна ли интеграция с МФЦ/ЕДДС и в каком виде?
4. Кто отвечает за эксплуатацию и обновление данных?

## 6. Рекомендация

Вариант **B**: локальное хранение в браузере, обезличенные данные, экспорт/импорт JSON, ручной выбор роли. Это даёт практическую ценность без хостинга и без обработки реальных ПД; переход к варианту C возможен позже, когда появится ответ на вопросы раздела 5.
