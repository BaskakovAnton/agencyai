# Единый приём обращений к депутату из пяти каналов: технико-правовое обоснование

| Поле | Значение |
|---|---|
| Статус | **НА СОГЛАСОВАНИЕ** (исследование выполнено) |
| Дата | 28.11.2026 |
| Область | Собственная (in-house) система: единая веб-форма + ВКонтакте, Одноклассники, MAX, Telegram, WhatsApp |
| Метод | Первоисточники через прямой доступ к страницам: официальная документация платформ и правовые базы. Поисковый сервис в среде недоступен, поэтому список источников ограничен теми, что открылись |
| Обозначения | **[ФАКТ]** — подтверждено источником; **[РЕШЕНИЕ]** — архитектурная рекомендация; **[РИСК]** — неподтверждённое или противоречивое; **[ВОПРОС]** — требует внешнего уточнения |

## 1. Резюме для руководителя

1. **Два потока обращений обязательны и должны быть разделены в интерфейсе и в данных.** Официальное обращение по 59-ФЗ требует идентификации отправителя; сообщение в мессенджере официальным обращением не становится. Смешение потоков создаёт ложные ожидания и правовые риски: гражданин считает, что «написал обращение», а юридически это переписка. **[ФАКТ]** — поправки в 59-ФЗ (№ 547-ФЗ) вступили в силу **30.03.2025**; **[РЕШЕНИЕ]** — в системе два явных статуса: `official` и `operational`, с разными сроками, шаблонами и учётом.
2. **ЕСИА нужна не «вообще», а только для официального потока.** Депутат не является госорганом, поэтому собственная система не обязана быть государственной информационной системой с ЕСИА: корректный путь — либо собственная форма с идентификацией через ЕСИА (если депутат подключится как оператор), либо **перенаправление** гражданина на официальную электронную приёмную (Госдума/регион) с сохранением текста. Выбор зависит от статуса депутата и должен быть подтверждён юристом. **[ВОПРОС]**
3. **Технически все пять каналов достижимы, но зрелость API разная.** Подтверждено первоисточниками: VK Callback API (до 10 серверов, событие `confirmation`), Telegram Bot API (`setWebhook`, `certificate`, `getWebhookInfo`), OK Bot API для групповых чатов (webhook, токен группы, выдаёт администратор), MAX API (`https://platform-api2.max.ru`, HTTPS, токен в заголовке `Authorization`, подписки `POST /subscriptions`, требование доверенных сертификатов). WhatsApp — по документации Meta, которая из этой среды не открылась. **[РИСК]**
4. **Рекомендуемая архитектура — тонкий приём и одна очередь.** Ingestion API принимает вебхуки всех каналов, проверяет подлинность, кладёт нормализованное сообщение в очередь, воркеры пишут в PostgreSQL и объектное хранилище; помощники работают в едином inbox. Такой контур не зависит от доступности каналов и переживает их всплески. **[РЕШЕНИЕ]**
5. **MVP — три канала и два потока.** Единая веб-форма (основной канал, включая официальный поток) + ВКонтакте + Telegram как самые предсказуемые API; OK и MAX — вторым этапом (по ним есть датированные ограничения), WhatsApp — третьим (шаблоны, окно 24 часа, верификация бизнес-аккаунта). **[РЕШЕНИЕ]**

## 2. Правовое заключение

### 2.1. Два потока: официальное обращение и оперативное сообщение

| Признак | Официальное (`official`) | Оперативное (`operational`) |
|---|---|---|
| Основание | 59-ФЗ | Переписка депутата с гражданином, юридического статуса обращения не имеет |
| Идентификация | Обязательна (ЕСИА / официальный сайт / информационная система с идентификацией) | Не требуется, но фиксируется канал и внешний идентификатор |
| Сроки | Законные сроки рассмотрения | Внутренний регламент помощника, без юридических сроков |
| Ответ | Официальный ответ по правилам 59-ФЗ | Ответ в том же канале, если он технически возможен |
| Регистрация | В журнале обращений с номером | В том же inbox, но с пометкой «не является обращением» |

**[РЕШЕНИЕ] Формулировки для интерфейса (проверить у юриста):**

- В веб-форме: «Отправить официальное обращение» и «Написать оперативно» — два разных действия с разными экранами, а не переключатель в одной форме.
- В каналах-мессенджерах автоответ: «Сообщение получено как оперативное. Оно не является официальным обращением по 59-ФЗ. Чтобы подать официальное обращение, перейдите: <ссылка на форму с идентификацией>».
- В карточке обращения сотруднику: явный бейдж `official` / `operational`, чтобы сроки и шаблоны не путались.
- Запрещено называть оперативное сообщение «обращением» в интерфейсе и в автоответах — это главный источник ложных ожиданий.

### 2.2. ЕСИА и статус депутата

- **[ФАКТ]** Поправки № 547-ФЗ к 59-ФЗ действуют с **30.03.2025** (подтверждено списком изменений в правовой базе).
- **[ФАКТ по вводной]** Электронное обращение рассматривается официально, если оно направлено через ЕСИА / официальный сайт / систему с идентификацией и аутентификацией.
- **[РЕШЕНИЕ]** Для депутата возможны три модели, выбор — за юристом:
  1. **Перенаправление** (минимальные риски, минимум работ): своя форма принимает текст, объясняет, что это оперативное сообщение, и предлагает перейти в официальную приёмную для официального обращения.
  2. **Своя форма + ЕСИА** (если депутат имеет право/возможность подключения): официальный поток целиком в своей системе.
  3. **Гибрид**: официальный поток — только через официальную приёмную; своя система ведёт оперативные и хранит ссылку на поданное официальное обращение.
- **[ВОПРОС]** Различия для депутата Госдумы, регионального и муниципального уровня: полномочия и доступ к ЕСИА различаются; требуется письменная позиция юриста и уточнение у аппарата.

### 2.3. 152-ФЗ: что применяется к нашей системе

Даже оперативное сообщение почти всегда содержит персональные данные (имя, телефон, адрес, фото). Значит, система — оператор ПД. **[РЕШЕНИЕ] Минимальный набор мер:**

| Требование | Что делаем |
|---|---|
| Правовое основание обработки | Согласие субъекта (галочка в форме и текст в боте), политика обработки ПД опубликована |
| Локализация баз данных | Основная БД и объектное хранилище — на серверах в РФ |
| Уведомление РКН | Уведомление об обработке ПД до начала обработки |
| Безопасность | Шифрование каналов (TLS), шифрование дисков, разграничение доступа, журнал доступа к обращениям |
| Хранение и удаление | Сроки хранения, удаление по достижении цели, обезличивание для аналитики |
| Поручения обработчикам | Договоры с хостингом/провайдерами, запрет передачи третьим лицам |

**[РИСК]** Тексты статей 152-ФЗ в этой среде первоисточником не открылись (портал РКН отдаёт только навигацию). Формулировки и точные ссылки на статьи нужно сверить по официальному тексту перед публикацией политики.

### 2.4. Риски правового контура

1. Гражданин воспринимает ответ в мессенджере как официальный → жалоба на бездействие. Снимается формулировками и статусами. **[РИСК]**
2. Публикация ответов/обращений без согласия → нарушение 152-ФЗ и врачебной/семейной тайны. Снимается запретом публикации по умолчанию. **[РИСК]**
3. Хранение переписки в зарубежных облаках → нарушение локализации. Снимается хостингом в РФ. **[РИСК]**
4. Обработка ПД детей/специальных категорий → повышенные требования. Нужна отдельная проверка. **[ВОПРОС]**

## 3. Референсная архитектура

```
Каналы            Приём                    Обработка                Хранение            Люди
─────────         ───────────────          ────────────────         ────────────        ──────────
Веб-форма  ─┐
VK         ─┤     Ingestion API          Очередь (одна)           PostgreSQL          Admin UI
OK         ─┼──▶  • проверка подписи  ──▶ • воркеры-нормализаторы ─▶ • appeals          • единый inbox
MAX        ─┤     • дедупликация          • антивирус вложений       • messages          • статусы, категории
Telegram   ─┤     • rate limit            • маршрутизация            • attachments       • шаблоны ответов
WhatsApp   ─┘     • ответ 200 быстро      • ответ в канал            • channel_identities• аудит доступа
```

**[РЕШЕНИЕ] Ключевые принципы:**

1. **Приём отделён от обработки.** Вебхук отвечает `200` максимально быстро (лимиты платформ), вся работа — в очереди. Платформа, не получившая `200`, повторяет доставку — это штатный источник дублей.
2. **Идемпотентность по `(channel, external_message_id)`.** Уникальный индекс в БД + `INSERT ... ON CONFLICT DO NOTHING`. Это единственный надёжный способ не задвоить сообщения при ретраях.
3. **Очередь — с «мёртвыми» письмами.** Ретраи с нарастающей задержкой; после N попыток — dead-letter с алертом. На старте достаточно PostgreSQL-очереди (SKIP LOCKED); брокер вводится при росте нагрузки.
4. **Вложения — в объектное хранилище, метаданные — в БД.** Файлы не хранятся в БД; при выдаче — подписанные ссылки с коротким сроком.
5. **Ответ в канал — отдельная подсистема.** Не все каналы позволяют инициативный ответ: учитываем окна и шаблоны (WhatsApp), права бота (VK/OK/MAX), недоступность канала (retry).

## 4. Матрица каналов

| Канал | Тип API | Верификация входящих | Ограничения | Вложения | Исходящий ответ |
|---|---|---|---|---|---|
| **Веб-форма** (основной) | Свой Form API | CSRF-токен, капча, rate limit по IP, подпись сессии | Размер файлов, типы, антивирус | Да, через свой upload | Email/личный кабинет/ссылка-статус |
| **ВКонтакте** | Callback API (webhook) | Событие `confirmation` при подключении, секрет сообщества, проверка источника | До 10 серверов Callback, набор событий на сервер, нужны права администратора сообщества | Вложения приходят ссылками; срок жизни ссылок ограничен — скачивать сразу | Да, сообщения сообщества в диалоге |
| **Одноклассники** | Bot API (Graph API) для групп, webhook | Токен группы `access_token`; проверка источника — уточнить | Токен выдаёт администратор группы на полной версии сайта; функциональность сообщений групп развивается | Уточнить по документации | Да, ответ в групповом чате от имени группы |
| **MAX** | HTTPS API `https://platform-api2.max.ru` | Токен бота в заголовке `Authorization` (query-параметры не поддерживаются); подписки `POST /subscriptions` | Только HTTPS; требуется доверенный сертификат (в документации — сертификат Минцифры); изменения API датированы: с июня 2026 `GET /chats` не поддерживается, с 9 сентября 2026 ограничен `POST /chats/{chatId}/members` | Уточнить по документации | Да, методы `/messages` |
| **Telegram** | Bot API, webhook | `setWebhook` с секретным путём; поддержка `certificate` для самоподписанных; `getWebhookInfo` для контроля | Лимиты Bot API, `pending_update_count` как индикатор отставания | Да, `getFile` | Да, `sendMessage` |
| **WhatsApp** | WhatsApp Business Cloud API, webhook | `X-Hub-Signature-256` (по вводной) | 24-часовое окно на свободный ответ, далее только шаблоны; верификация бизнес-аккаунта | Да | Только в окне или шаблонами |

**Что подтверждено первоисточниками:** VK — событие `confirmation`, до 10 серверов, набор событий; Telegram — `setWebhook`, `certificate`, `getWebhookInfo`, `pending_update_count` (по зеркалу справочника); OK — webhook, токен группы, выдача администратором; MAX — HTTPS, заголовок `Authorization`, подписки, доверенные сертификаты, датированные изменения. **[ФАКТ]**
**Что не подтверждено из этой среды:** точный параметр `secret_token` Telegram в доступном зеркале отсутствовал (возможно, зеркало старее официального справочника); документация Meta (WhatsApp) недоступна; детали вложений OK и MAX. **[РИСК]**

## 5. Модель данных и API-контракты

### 5.1. Минимальная схема

```sql
appeals(id, public_number, stream, status, category, channel, subject, created_at, due_at, assignee_id, citizen_name, citizen_contact, consent_at)
messages(id, appeal_id, direction, channel, external_message_id, author_external_id, text, sent_at, received_at, raw_payload_ref)
attachments(id, message_id, kind, file_name, mime, size, storage_key, scan_status, sha256)
channel_identities(id, channel, external_user_id, display_name, citizen_id, verified_at, last_seen_at)
outbox(id, appeal_id, channel, payload, status, attempts, next_attempt_at, last_error)
audit_log(id, actor_id, action, entity, entity_id, at, ip, details)
-- дедупликация входящих:
CREATE UNIQUE INDEX ux_messages_channel_external ON messages(channel, external_message_id);
```

**[РЕШЕНИЕ] Правила:** `stream` — `official` | `operational`; `status` — `new` → `in_progress` → `waiting_citizen` → `answered` → `closed` (+ `spam`, `duplicate`). `raw_payload_ref` хранит исходный вебхук для разбора спорных случаев, но не в основной таблице.

### 5.2. Эндпоинты

| Эндпоинт | Назначение | Особенности |
|---|---|---|
| `POST /ingest/vk` | вебхук сообщества | сначала ответ на `confirmation`, затем проверка секрета |
| `POST /ingest/telegram` | вебхук бота | проверка секретного пути/заголовка, быстрый `200` |
| `POST /ingest/ok` | вебхук группы | проверка токена/источника |
| `POST /ingest/max` | уведомления MAX | заголовок `Authorization`, обработка подписок |
| `POST /ingest/whatsapp` | вебхук Cloud API | `X-Hub-Signature-256`, ответ на верификацию `GET` |
| `POST /api/appeals` | веб-форма: оперативное сообщение | капча, rate limit, согласие на обработку ПД |
| `POST /api/appeals/official` | веб-форма: официальное обращение | идентификация (ЕСИА или переход в официальную приёмную) |
| `GET /api/appeals/{number}/status` | статус для гражданина | доступ по одноразовой ссылке/коду |

## 6. Безопасность и 152-ФЗ: чек-лист

- [ ] Проверка подлинности каждого вебхука (секрет/подпись/токен) — до любой обработки; при провале — `403` и запись в журнал.
- [ ] Ограничение частоты: по IP для формы, по внешнему пользователю для ботов; капча после порога.
- [ ] Ограничения файлов: белый список MIME, лимит размера, антивирусная проверка, `scan_status` до выдачи человеку.
- [ ] RBAC: помощник видит только назначенные обращения; руководитель — все; аудит каждого просмотра и действия.
- [ ] Разграничение по каналам/категориям (например, обращения с ПД детей — отдельная категория доступа).
- [ ] Логи без ПД (в логи — идентификаторы, не текст обращения).
- [ ] Резервное копирование с шифрованием и проверкой восстановления.
- [ ] Политика хранения и удаления, обезличивание для отчётности.
- [ ] Уведомление РКН, публикация политики обработки ПД, согласия в форме и в ботах.
- [ ] Хостинг и хранилище — в РФ (локализация).
