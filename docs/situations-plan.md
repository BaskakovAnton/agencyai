# План: перенос 37 ситуаций регламента

## Откуда берём

`deput` содержит одни и те же 37 ситуаций в четырёх копиях, которые уже разошлись.
Переносим **одну согласованную версию**, собранную из самой полной копии каждого поля:

| Поле | Источник |
|---|---|
| id, раздел (8.1–8.4), заголовок, приоритет, текст SLA | `index.html` (структура разделов) |
| шаги: лейн (роль) + заголовок + пояснение | `player.html` (самый полный формат, включает лейн жителя) |
| связь «узел процесса ↔ ситуации» | `matrix.html` (30 узлов) |

Перенос делает **скрипт** `scripts/import-situations.ts`, а не ручной набор: он читает клон
`deput`, извлекает данные и раскладывает их по файлам разделов. Так результат воспроизводим:
перезапуск скрипта даёт те же файлы.

## Модель

```ts
Situation { id: "С9", section: "during", title, summary, priority, sla, steps: SituationStep[] }
SituationStep { lane: RoleId, title, text }
```

Файлы: `src/data/situations/before.ts` (8), `during.ts` (20), `contractors.ts` (5), `feedback.ts` (4),
агрегат `src/data/situations.ts` (+ `SECTION_TITLES`, `situationById`), связи `src/data/situation-nodes.ts`.

**Разделение труда:** скрипт генерирует только данные — файлы разделов `src/data/situations/*.ts` и связь
`src/data/situation-nodes.ts`; агрегат `src/data/situations.ts` (поиск, гибкие ссылки, обратный поиск узлов)
написан руками и скриптом не перезаписывается.

## Что меняется в модели

- у заявки появляется `situationId`: каждая заявка «проигрывает» ситуацию регламента;
- приоритет заявки берётся из ситуации (в `deput`: 4 аварийных, 18 неотложных, 1 сезонная, 14 вне SLA),
  а не из категории инцидента (категория остаётся источником текста и адреса);
- в CLI: `situations` — список по разделам, `situation С9` — карточка с шагами и узлами;
- на странице: у выбранной заявки видны её ситуация, шаги по ролям и связанные узлы.

## Проверяем тестами

1. Ровно 37 ситуаций, id идут С1…С37, разделы: 8 / 20 / 5 / 4.
2. У каждой: заголовок, summary, приоритет из четырёх, непустой SLA, ≥2 шага; лейн — валидная роль, текст непустой.
3. Связь с узлами: `situationsForNode("U12")` = С13, С14, С15, С17; `situationsForNode("U30")` = С5, С20, С23.
4. Карта узлов покрывает все 30 узлов, ссылки на ситуации существуют.
5. Генератор: у каждой заявки есть `situationId` из С1…С37, приоритет совпадает с ситуацией, распределение не вырождено.
6. Детерминизм генератора сохраняется.
7. CLI: `situations` печатает 37 строк; `situation С9` показывает заголовок, SLA и шаги.
8. Страница: карточка заявки содержит её ситуацию и хотя бы один шаг.
