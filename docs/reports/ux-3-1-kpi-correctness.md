# UX-3.1 · Аудит и исправление корректности KPI и жизненного цикла завершения

**Статус:** ACCEPTED WITH LIMITATIONS · коммит и push **не делались** (по условию задания).

## 1. Цель

Привести периодную аналитику Dashboard к достоверности: одна бизнес-семантика на показатель, единое правило расчёта во всех периодах, согласованность Dashboard ↔ реестр ↔ карточка.

## 2. Выявленные ошибки и причины

| № | Проблема | Файл | Причина |
|---|---|---|---|
| 1 | Карточка «Требуют внимания» показывала `kpi.attention`, а её динамику считала по `overdue` | `src/web/dashboard-html.ts` | в реестре KPI отсутствовал показатель `attention` |
| 2 | `flow.finished` считалось по достижению терминального узла графа | `src/core/analytics/flow.ts` | завершение отождествлялось с графовым состоянием, а не с подтверждением контролёра |
| 3 | Обращение на терминальном узле, ожидающее проверки, попадало в `finished` и терялось из `pendingReview` | `src/core/analytics/snapshot.ts` | проверка `isFinished` стояла раньше проверки жизненного цикла и делала `continue` |
| 4 | Отчёт UX-3 «не найден» по утверждению задания | `docs/reports/` | **проблема не подтвердилась:** `docs/reports/ux-3-kpi-periods.md` (14,2 КБ) присутствует в `main`; ссылка в журнале корректна

Дополнительно найденное при аудите: карточка обращения показывала **текущий** статус жизненного цикла, тогда как Dashboard — состояние **на выбранную дату** (расхождение представлений §8).

## 4. Новые и изменённые тесты

- `tests/kpi-attention.test.ts` — 4 сценария: внимание ≠ просрочка; дельта внимания сравнивает внимание; рост просрочки без изменения внимания; нулевая база.
- `tests/kpi-completion.test.ts` — 8 сценариев: терминальный узел без подтверждения; ожидание проверки на терминальном и нетерминальном узле; подтверждение; отказ; переоткрытие; **историческая таблица Snapshot** (3/4/5/6/7 января); разделение `reachedTerminal` и `finished`; дата завершения.
- `tests/kpi-consistency.test.ts` — 3 сценария: Dashboard = доменный Snapshot на трёх датах; статус карточки = статус на дату для всех 30 обращений; реестр не противоречит Snapshot.
- Красные тесты до исправления: **9 из 12 падали** (`attention` отсутствовал, `reachedTerminal` отсутствовал, терминальный узел считался завершением, исторические срезы переписывались).

## 5. Правила расчёта после исправлений

| Показатель | Правило |
|---|---|
| `snapshot.finished` | последняя применимая запись жизненного цикла — `approved` |
| `snapshot.active` | всё остальное: в работе, `pending_review`, переоткрыто, после отказа |
| `snapshot.pendingReview` | статус на дату = `pending_review` |
| `snapshot.attention` | единое правило `needsAttention` (просрочка или срочная незавершённая), только активные |
| `flow.finished` | подтверждения (`approved`) в периоде; `flow.reachedTerminal` — достижения терминального узла |
| `inTimeShare` | доля подтверждений без нарушения норматива на дату подтверждения |
| динамика по дням | `created` — создание, `finished` — подтверждение, `reachedTerminal` — терминальный узел |
| сравнение | Snapshot сравнивается с Snapshot, Flow с Flow; процент не считается при нулевой базе |

## 7. Известные ограничения

1. Обращения без записей жизненного цикла завершёнными не считаются: молчаливого авто-подтверждения нет (решение за владельцем).
2. Панель подтверждения предлагает действия по **текущему** состоянию, а показывает статус **на выбранную дату** — так и подписано; окончательную проверку всё равно делает домен.
3. Рейтинг подразделений по SLA по-прежнему не строится (атрибуция просрочки недостоверна).
4. Тач-цели меньше рекомендованных (2837 замеров) — существовавшая особенность компактных контролов, не регрессия UX-3.1.

## 8. Вопросы владельцу

1. Считать ли обращение завершённым, если оно достигло терминального узла, но записей жизненного цикла нет (сейчас — нет)?
2. Нужно ли показывать `reachedTerminal` отдельным показателем на Dashboard или достаточно примечания в блоке «Как считаем»?
3. Нужно ли ограничивать действия подтверждения датой среза (сейчас домен проверяет текущее состояние)?
