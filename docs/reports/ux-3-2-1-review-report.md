## 6. Анализ фильтрации

**Статус на дату.** `buildRows` (строки 122–160) применяет `matchesView` из нового модуля, где завершённость и ожидание проверяются через `lifecycleStatusOn` на дату среза. Проба по четырём датам: строк `view=review` = `snapshot.pendingReview` (1 / 2 / 6 / 6), тогда как расчёт по **текущему** статусу дал бы 6 на всех датах. Регрессии текущего дня нет (02.01 и 08.01 совпадают по обоим способам).

**Смена статуса во времени.** На фикстуре с переходами (`tests/lifecycle-fixture.ts`) `lifecycleStatusOn` даёт корректную последовательность: submitted 04.01 → `pending_review`, approved 05.01 → `completed`, reopened 07.01 → `reopened`; отказ 06.01 → `active`. Это подтверждает, что фильтр очереди не «залипает» на текущем статусе.

**Подразделения.** Проба на 02.01.2026: всего 28 строк = 13 (`DEP-HOUSING`) + 4 (`DEP-CONTROL`) + 6 (`DEP-DISPATCH`) + 1 (`DEP-ROADS`) + 1 (`DEP-LIGHT`) + 3 без ответственного — точное разбиение без пересечений и потерь; внутри каждого фильтра все строки действительно соответствуют `accountableOf`. Неизвестный код (`DEP-НЕТ`) → фильтр игнорируется (28 строк), пустое значение → 28, `department=none` → ровно 3 обращения без активного ответственного. Подмена автора обращения или исполнителя не происходит: используется только `accountableOf`.

## 7. Анализ filtersHash

Фактическая семантика (`src/web/incidents.ts:61–76`): канонический сериализатор состояния реестра. Свойства, подтверждённые пробой:

- детерминированность: одинаковый набор фильтров → одинаковый hash, независимо от порядка параметров во входном адресе;
- канонизация: legacy-адрес и адрес с иным порядком дают один и тот же hash;
- нет потери значимых фильтров: при изменении одного поля остальные семь сохраняются;
- нет коллизий среди представимых состояний (`view=all` и пустой `department` просто опускаются, как и `sort=id`);
- hash не создаёт «декоративных» различий (значения кодируются `URLSearchParams` единообразно).

Неизвестные query-параметры в hash не переносятся — см. F4.
