## 3. DEC-03 — семантика очереди подтверждений

### 3.1. Как считается счётчик

- **FACT:** отображаемое значение — `overview.org.waitingForReview`, которое формирует `orgFactsFor(org, visibleIdsOnDay)` (`org-integration.ts:89–92`), а сам счётчик (`org-integration.ts:85`) фильтрует по **текущему** `lifecycleOf(id).status === "pending_review"`.
- **FACT:** список очереди в реестре (`view=review`) считает статус **на дату** через `matchesView` → `isPendingReviewOn` → `lifecycleStatusOn` (`src/web/incidents-view-filter.ts:20–32`, `src/core/analytics/snapshot.ts:32–42`).
- **FACT:** `snapshotOn(...).pendingReview` — тоже статус на дату.
- **FACT:** для обращения без записей жизненного цикла статус не выводится, и оно не попадает в очередь.

### 3.2. Проверка значения DEC-03 на данных (все 25 дней окна)

Измерено сравнение трёх величин на каждом дне: счётчик обзора (текущий статус по видимым), `snapshot.pendingReview` (на дату), число строк `view=review`.

| День | Видимых | Счётчик обзора | snapshot.pendingReview | Строк `view=review` | Совпадает |
|---|---|---|---|---|---|
| 2025-12-20 | 2 | 0 | 0 | 0 | да |
| 2025-12-21 | 4 | 1 | 1 | 1 | да |
| 2025-12-22 | 6 | **1** | **2** | 2 | **НЕТ** |
| 2025-12-23 | 8 | **2** | **1** | 1 | **НЕТ** |
| 2025-12-28 | 17 | **4** | **3** | 3 | **НЕТ** |
| остальные 21 день (24.12–27.12, 29.12–13.01) | 10–30 | совпадает | совпадает | совпадает | да |

**FACT:** расхождение есть на **3 днях из 25** (22.12, 23.12, 28.12), величина расхождения 1–2 обращения. **FACT:** число строк `view=review` совпадает с `snapshot.pendingReview` **на всех 25 днях** — то есть список очереди уже исторически корректен, расходится только отображаемый счётчик.

**Пример расхождения (22.12):** счётчик 1 против очереди 2. Отличается обращение `З-005`: записи `submitted@2025-12-22, approved@2025-12-23, reopened@2025-12-23`; на 22.12 статус `pending_review`, текущий статус `reopened`. Счётчик по текущему статусу его не видит, очередь по статусу на дату — видит.

**Важное уточнение к предыдущему аудиту (FACT → коррекция):** в отчёте UX-3.2.1 было зафиксировано «на 21.12 счётчик 6, очередь 1». Это измерение относилось к значению функции `waitingForReview(org, все 30 обращений)` (6), а **не** к отображаемому счётчику: дашборд передаёт в неё только **видимые на дату** обращения, поэтому на 21.12 отображаемый счётчик равен 1 и совпадает с очередью. Тезис DEC-03 подтверждается, но формулировка и значения в исходном аудите были неточны.

### 3.3. Что означает «очередь подтверждений» сейчас

**INFERENCE:** фактическая семантика смешанная: список = «обращения, ожидавшие подтверждения на выбранную дату», счётчик = «видимые на дату обращения, у которых ожидание подтверждения продолжается **сегодня**». Это разные вопросы, и ни один из них не сформулирован в спецификации явно.

## 7. Проблемы и ограничения

1. **P1 (FACT):** счётчик «Ждут подтверждения» использует текущий статус, очередь — статус на дату; расхождение 1–2 обращения на 3 днях из 25. Исправление — одна строка в `overview.ts`/`org-integration.ts` (перевести счётчик на `snapshot.pendingReview`), но это меняет видимое значение → нужно продуктовое решение (DEC-03).
2. **P2 (FACT):** KPI-карточки не интерактивны, ссылки теряют контекст, разрез подразделений статичен — переходов «показатель → причина» нет.
3. **UNKNOWN:** бизнес-смысл «очереди подтверждений» на историческую дату продуктово не зафиксирован (см. варианты A/B/C в спецификации).
4. **Ограничение модели:** атрибуция подразделения (`accountableOf`) дана на текущий момент (ограничение F5 аудита UX-3.2.1), поэтому переход `department=<id>` исторически не разрешён по дате.
5. **Ограничение данных:** у обращений без записей жизненного цикла статус отсутствует — они не попадают ни в счётчик, ни в очередь (FACT, осознанное ограничение UX-3.1).
