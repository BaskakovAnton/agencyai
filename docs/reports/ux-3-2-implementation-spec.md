## 1. Executive Summary

ТЗ описывает шесть функциональных требований (FR-01…FR-06), пять нормативных контрактов (§8–§12) и шесть утверждённых решений владельца (§5). Ключевая идея — связать показатель с **тем же множеством обращений**, из которого он посчитан: переходы используют доменные функции (`needsAttention`, `lifecycleStatusOn`, `slaPhaseOnDay`), а не похожие фильтры.

Доказанные дефекты, исправляемые в этапе:

1. **Счётчик очереди подтверждений ≠ содержимое очереди.** `waitingForReview` (`src/web/org-integration.ts:85`) считает **текущий** статус и даёт 6 на любой день; `snapshotOn(...).pendingReview` и очередь считают статус **на дату**: 21.12 — 1, 25.12 — 2, 31.12 — 5, 02.01 — 6 (значения подтверждены повторным замером).
2. **Даты вне окна модели обрабатываются четырьмя способами:** `chat-view.ts:21` и `timeline-view.ts:25` молча подменяют день последним, `dashboard-view.ts:18` и `incidents-view.ts:12` дают пустое состояние, `incident-view.ts:26` рендерит фантомный этап («U2 · Уточнение у жителя», «Нет SLA»), а селектор показывает 20.12.2025.

Объём: 6 требований, 6 решений владельца, 5 сценариев, 5 контрактов, 7 этапов, 3 новых модуля представления, 1 этап декомпозиции под лимит 200 строк. Домен (`src/core`, `src/data`) не меняется.

## 2. Цели UX-3.2

1. Переход от показателя к точному набору обращений одним действием.
2. Контекст перехода сохраняется в адресе и воспроизводится при перезагрузке.
3. Подразделение — аналитический разрез (объём и сроки), не рейтинг.
4. Очередь подтверждений: явная точка входа и единый источник истины для счётчика и списка.
5. Карточка отвечает: кто действует сейчас и сколько длится этап — по фактическим событиям.
6. Даты вне окна модели дают единое честное состояние.

## 6. Карта пользовательских сценариев

### Сценарий 1. Руководитель обнаружил проблему
Обзор → KPI «Требуют внимания» → реестр `view=attention` → карточка → видит действующего и длительность этапа.
**Критерий успеха:** множество совпадает с `snapshot.attention` на ту же дату; в карточке указаны текущий этап, действующий и длительность.

### Сценарий 2. Руководитель анализирует подразделение
Обзор → «Ответственные подразделения» → реестр `department=<id>` → обращения → возврат кнопкой браузера.
**Критерий успеха:** число строк равно факту по подразделению; «Без ответственного» показывается только при ненулевом количестве; возврат сохраняет предыдущий адрес.

### Сценарий 3. Руководитель проверяет подтверждения
Обзор → «Ждут подтверждения» → реестр `view=review` → карточка → решение по существующим доменным правилам.
**Критерий успеха:** значение счётчика равно числу строк очереди на 21.12 / 25.12 / 31.12 / 02.01; при нуле — явное состояние.

### Сценарий 4. Анализ длительности этапа
Карточка → «Текущий этап» → «Действует сейчас» → «Этап длится N ч» → история с длительностями завершённых этапов.
**Критерий успеха:** длительности совпадают с расчётом по событиям для семи описанных случаев; при неполной истории — «Нет данных».

### Сценарий 5. Дата вне окна модели
Пользователь выбирает `?at=2020-01-01` (дата остаётся выбираемой) → единое состояние недоступности данных с границами окна и переходом к ближайшей доступной дате.
**Критерий успеха:** на всех пяти экранах одинаковый текст и признак `data-outside-window`; фантомных этапов, SLA и действий нет.

## 7. Функциональные требования FR-01…FR-06

### FR-01. Контекстные переходы с KPI

| KPI | Доменное условие | Переход | Обоснование |
|---|---|---|---|
| Активные обращения | `snapshot.active`: видимые на дату и не `completed` по `lifecycleStatusOn` | `view=active` | управленческая нагрузка, нужен состав |
| Требуют внимания | `snapshot.attention`: активные, где `needsAttention(graph, incident, day)` | `view=attention` | главный сценарий «где проблема» |
| Просроченные | `snapshot.overdue`: активные с `slaPhaseOnDay === "overdue"` | `view=overdue` | список для эскалации |
| Ждут подтверждения | `snapshot.pendingReview`: активные со статусом на дату `pending_review` | `view=review` (DEC-02, DEC-03) | очередь решения контролёра |
| На паузе | `snapshot.paused`: активные с фазой `paused` | `view=paused` | объясняет зависшие обращения |
| Завершено за период | `flow.finished` — поток периода | **перехода нет** (DEC-01) | набор строк не определён однозначно |
| Динамика, дельта остатка, доля в срок | производные потока | **перехода нет** | не соответствует множеству строк |

Дополнительные переходы: строка «Ждут подтверждения» в панели «Контроль сроков» → `view=review`; элемент разреза подразделений → `department=<id>`; ссылка панели внимания → `view=attention`.
**Запрещено** реализовывать «похожий» фильтр: источник истины — те же доменные функции.

### FR-02. Сохранение контекста в URL

Контекст (`at`, `view`, `department`, существующие `q`/`priority`/`sla`/`node`/`sort`/`period`) живёт в hash; `parseFilters` — единственная точка разбора, `filtersHash` — формирования. «Источник перехода» отдельным параметром не вводится. Обычный реестр — `#incidents` или `#incidents?at=<день>`.
**Нормативный контракт:** §8.

### FR-03. Подразделения как аналитический разрез

Фильтр по активному ответственному подразделению; факты только из достоверных данных; **рейтинг запрещён**; категория «Без ответственного» показывается лишь при ненулевом количестве (DEC-05); обращения без атрибуции остаются в общих показателях.
**Нормативный контракт:** §9.

### FR-04. Очередь подтверждений

Условие — статус **на дату** `pending_review`; точка входа — контекстный фильтр реестра; счётчик и список используют одно условие (DEC-03); канонический параметр `view=review` (DEC-02).
**Нормативный контракт:** §10.

### FR-05. Карточка: действующий и длительности

Блок «Действует сейчас» показывается всегда; при отсутствии подтверждённого ответственного выводится «Ответственный не определён» (DEC-06). Длительности считаются по фактическим событиям с учётом семи описанных случаев; неполная история даёт «Нет данных».
**Нормативный контракт:** §11.

### FR-06. Даты вне окна модели

Даты остаются выбираемыми; вне окна модели показывается единое состояние недоступности; подмена дня и фантомные состояния запрещены (DEC-04). Исторический режим UX-3.1.x сохраняется.
**Нормативный контракт:** §12.

## 8. Контракт URL и фильтров

| Параметр | Допустимые значения | Валидация | Некорректное значение |
|---|---|---|---|
| `at` | `YYYY-MM-DD` | формат; вне окна → состояние §12 | вне окна: явное состояние, подмена запрещена |
| `view` (новый, канонический) | `active` \| `attention` \| `overdue` \| `paused` \| `review` \| `unassigned` | белый список | игнорируется |
| `review` (существующий) | `pending` | **только чтение как алиас**: `review=pending` ≡ `view=review` | игнорируется |
| `department` (новый) | `DEP-*` из справочника \| `none` | проверка по `directory.departments` + спецзначение | игнорируется, показывается всё |
| `q` | строка | trim | пустая = без поиска |
| `priority` | `urgent`/`normal`/`routine`/`none` | белый список (существует) | игнорируется |
| `sla` | `SLA_PHASES` | белый список (существует) | игнорируется |
| `node` | id узла графа | проверка `graph.byId` | игнорируется |
| `sort` | `id`/`priority`/`date`/`urgency` | белый список (существует) | по умолчанию `id` |
| `period` | `7`/`30` | `isPeriodLength` (существует) | только обзор, по умолчанию 7 |

**Стратегия совместимости `review=pending` (DEC-02).** Параметр используется сейчас в: `src/web/incidents.ts` (поле фильтра, `parseFilters`, `filtersHash`, `buildRows`), `src/web/incidents-html.ts:88` (селект «Подтверждение»), `src/web/incidents-view.ts:48` (обработчик), `tests/incidents-html.test.ts:55`, `e2e/ux4.spec.ts:43–44` (выбор `pending` и проверка адреса). План: (1) `parseFilters` принимает `review=pending` и возвращает `view=review`; (2) `filtersHash` **перестаёт** писать `review`, пишет только `view`; (3) селект «Подтверждение» управляет `view` (значения `all`/`pending` сохраняются в UI, но в адрес пишется `view=review`); (4) `e2e/ux4.spec.ts` обновляется на проверку `view=review`; (5) старые ссылки (в отчётах и закладках) продолжают открывать ту же выборку. Удаление алиаса — отдельное решение после этапа.

Правила: `view` и `sla` могут сочетаться; неизвестные параметры не ломают экран; round-trip `filtersHash` → `parseFilters` возвращает исходный набор; `department` без `view` показывает все обращения подразделения.

## 9. Контракт аналитики подразделений

1. **Атрибуция:** только `accountableOf(incidentId)` — та же функция, что в `departmentDistribution` (`org-integration.ts:72`).
2. **Показатели на дату:** объём активных; просроченные среди активных; ожидающие подтверждения; обращения без исполнителя (активное назначение с `employeeId === null`).
3. **Категория «Без ответственного» (`department=none`)** показывается в блоке фактов **только если её количество больше нуля** (DEC-05); при нуле категория не выводится, но обращения остаются в общих показателях и в списке без фильтра.
4. **Запрещено:** средние значения, проценты эффективности, места, «лучше/хуже», сортировка по эффективности, слово «рейтинг».
5. **Пустое состояние:** при отсутствии назначений — «Назначения отсутствуют»; нули не выдаются за факт.

## 10. Контракт очереди подтверждений

1. **Условие попадания:** обращение видимо на дату **и** `lifecycleStatusOn(lifecycle, day) === "pending_review"` — та же функция, что в `snapshotOn`.
2. **Канонический параметр:** `view=review` (DEC-02); алиас `review=pending` только на чтение.
3. **Единый источник истины (DEC-03):** значение счётчика = `overview.analytics.snapshot.pendingReview`; список = результат `buildRows(..., view: "review")`. Оба используют `lifecycleStatusOn`. Текущая реализация `waitingForReview` (`org-integration.ts:85`, текущий статус) **удаляется из счётчика обзора**.
4. **Контрольные значения (проверено дважды):** 21.12 → 1; 25.12 → 2; 31.12 → 5; 02.01 → 6. Счётчик обзора обязан давать те же числа, что и очередь.
5. **Ноль:** счётчик 0, ссылка остаётся; в реестре — «Нет обращений, ожидающих подтверждения».
6. **Историческая дата:** очередь отражает состояние на дату; действия блокируются историческим режимом с существующим пояснением.
7. **После изменения состояния:** пересчёт при отрисовке; отдельная логика счётчика не создаётся.

## 11. Контракт текущего ответственного и длительности этапов

### 11.1. Кто есть кто (DEC-06)

| Понятие | Источник |
|---|---|
| Автор события | `Move.actor` |
| Последний исполнитель | `lastSubmitter(lifecycle.records)` (используется для запрета самоподтверждения) |
| Текущий ответственный | `accountableOf(incidentId)` → подразделение; исполнитель — активное назначение с `employeeId !== null` |
| Действует сейчас | роль узла на дату (`incidentAt(incident, day).nodeId` → `roleOf`) + текущий ответственный + исполнитель |

Блок «Действует сейчас» показывается **всегда**. Если ответственный не установлен — «Ответственный не определён». Подменять ответственного автором события, последним исполнителем или угадывать сотрудника по подразделению **запрещено**.

### 11.2. Длительности: семь случаев (нормативно)

Обозначения: `moves = historyUpTo(incident, day)` (порядок массива = контракт append-only); `movesWithAt` = только события с определённым `at`; `start(0) = createdAt`; `end(последнего) = day + "T23:59:59.999Z"` (конец выбранного модельного дня, не «сейчас»); `records = lifecycle.records` с `dayOf(record.at) <= day`.

| Случай | Начало интервала | Окончание | Длительность | Неполная история |
|---|---|---|---|---|
| 1. Повторное открытие (reopen) | последняя запись `reopened` из `records` | конец выбранного дня | «с момента решения контролёра: N ч» (отдельно от длительности этапа) | нет записи `approved`/`reopened` → показывается только длительность этапа |
| 2. Повторное прохождение этапа | `Move` этого входа | следующий `Move.at` или конец дня | отдельный интервал на каждый вход; агрегация не выполняется | нет следующего `Move` → текущий интервал |
| 3. Одинаковые timestamp | `Move` с тем же `at` | следующий `Move` | **0 ч** — допустимое значение, показывается как «0 ч» | порядок берётся из массива, сортировка запрещена |
| 4. Возврат на предыдущий этап | `Move` возврата | следующий `Move` | новый интервал; прежний визит сохраняет свою длительность | — |
| 5. Отклонение и повторная подача | запись `rejected` затем `submitted` | конец дня | интервалы состояния из `records` («с момента решения: N ч»), узел процесса не меняется | нет записей → «Нет данных» |
| 6. Исторический срез между событиями | последний `Move.at` или запись `records` ≤ дня | конец выбранного дня | интервал закрывается концом дня, а не реальным временем | будущие события не участвуют |
| 7. Нет события начала/окончания | `createdAt`, если `moves` пуст | конец дня | интервал от создания заявки | нет `createdAt` → «Нет данных» |

**Обязательные правила:** событие без `at` не участвует в расчёте длительности (показывается в истории без длительности); два потока событий (`Incident.history` — шаги процесса, `lifecycle.records` — решения по завершению) не смешиваются: этап считается по `history`, состояние подтверждения — по `records`; округление вниз до часов; отрицательные значения невозможны (события вне окна отфильтрованы датой); при невозможности достоверного расчёта выводится «Нет данных», а не подстановка.

## 12. Контракт дат вне окна модели (DEC-04)

1. Доступное окно — `days` из `story.days` (в демо 20.12.2025 — 13.01.2026).
2. **Даты остаются выбираемыми** в селекторе; выход за окно не блокируется.
3. `at` вне окна (или неизвестный день) → единое UI-состояние `data-outside-window`: данные не рендерятся, действия отсутствуют, выводится «Дата вне доступного периода: 20 декабря 2025 — 13 января 2026» и ссылка на ближайшую доступную дату.
4. Молчаливая подмена дня последним доступным **запрещена** (сейчас так делают `chat-view.ts:21` и `timeline-view.ts:25`).
5. Пустой `at` → последний доступный день (текущая модельная дата), состояния «вне окна» нет.
6. Обязательства: нет фантомных этапов; нет «Нет SLA» для несуществующего обращения; отсутствие данных не подменяется нулями; переписка не показывает пустое полотно без пояснения; действия недоступны.
7. Совместимость: `isHistoricalDay` не меняется; при `outside_window` индикатор исторического среза не показывается. Это **UI-состояние**, новое доменное состояние не вводится.

## 21. Риски и ограничения

1. **Лимит 200 строк:** `timeline-view.ts` (203) и `incident-html.ts` (196) — выделен этап UX-3.2.0 с нулевым изменением поведения; риск скрытого состояния `mountTimeline` снимается фабриками.
2. **Расширение `IncidentFilters`** и алиас `review=pending` затрагивают существующие тесты и e2e — обновление ожиданий только с обоснованием.
3. **Смена значения счётчика** (6 → 1 на 21.12) — намеренное исправление; фиксируется в отчёте этапа.
4. **Два потока событий** (`history` и `records`) — правило §11.2 обязательно; смешение даст недостоверные длительности.
5. **Неполная атрибуция** — подразделения как объём и сроки; рейтинг запрещён.
6. **Объём демо 28–30 обращений** — эффект проверяется на границах.
7. **Публикация** требует отдельного разрешения владельца.

## 22. Открытые вопросы владельцу

1. Удалять ли алиас `review=pending` после UX-3.2 (сейчас сохраняется только на чтение)?
2. Нужна ли отдельная семантика выборки «завершено за период», чтобы сделать KPI кликабельным позже (DEC-01 отложен)?
3. Показывать ли в истории длительность для событий без `at` (сейчас — без длительности, только запись)?
4. Нужен ли на обзоре отдельный показатель «обращения без ответственного», или достаточно факта в разрезе подразделений?

## 23. Рекомендация по порядку реализации

1. **UX-3.2.0** — декомпозиция под лимит (`timeline-view.ts`, `incident-html.ts`), проверяется одной регрессией.
2. **UX-3.2.1** — контракт URL и фильтров (фундамент переходов).
3. **UX-3.2.2** — единое поведение дат вне окна (DEC-04).
4. **UX-3.2.3** — контекстные переходы с обзора и единый счётчик очереди (DEC-01, DEC-03).
5. **UX-3.2.4** — подразделения как разрез (DEC-05).
6. **UX-3.2.5** — действующий и длительности (DEC-06), может идти параллельно с 3.2.3/3.2.4.
7. **UX-3.2.6** — интеграция, регрессия, отчёт; публикация — по отдельному разрешению.

После каждого этапа — остановка и решение владельца.
