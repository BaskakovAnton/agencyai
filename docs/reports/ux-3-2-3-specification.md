# UX-3.2.3 — спецификация (KPI, очередь подтверждений, контекстные переходы)

Основание: `docs/reports/ux-3-2-3-0-discovery.md`, `ux-3-2-implementation-spec.md`, реализация на `f7b5954`.
Помечено: FACT / INFERENCE / UNKNOWN. Ничего в этом документе не реализовано.

## 1. Scope

**Входит:** счётчик и список очереди подтверждений (единый источник истины), контекстные переходы с Dashboard в реестр, историческая семантика KPI. **Не входит:** изменение формул KPI, новые показатели, UI-контролы для `view`/`department` из UX-3.2.4, длительности и действующий из UX-3.2.5, мобильный редизайн, рейтинги подразделений.

## 2. Функциональные требования

### FR-01. Единый источник истины для очереди подтверждений (DEC-03)

- **Требование:** число, отображаемое как «Ждут подтверждения», и число строк `#incidents?view=review` на ту же дату совпадают на **всех** днях окна. FACT: сейчас совпадают на 22 днях из 25 и расходятся на 22.12, 23.12, 28.12 (1–2 обращения).
- **Алгоритм:** отображаемое значение = `buildOverview(...).analytics.snapshot.pendingReview`; функция `waitingForReview` (`src/web/org-integration.ts:85`) перестаёт использоваться для счётчика обзора (остаётся только как утилита либо удаляется вместе с полем `OrgFacts.waitingForReview`).
- **Не менять:** `lifecycleStatusOn`, `snapshotOn`, `matchesView` — семантика «статус на дату» уже верна (FACT: строки очереди совпадают со Snapshot на всех 25 днях).
- **Нулевое состояние:** при 0 счётчик показывает 0, ссылка остаётся рабочей (пустое состояние реестра с кнопкой сброса).
- **Вне окна модели:** счётчика нет — экран показывает единое состояние `data-outside-window` (UX-3.2.2).

### FR-02. Контекстные переходы с Dashboard

| Источник | Целевой URL | Обоснование |
|---|---|---|
| KPI «Активные обращения» | `#incidents?at=<день>&view=active` | состав нагрузки на дату |
| KPI «Требуют внимания» | `#incidents?at=<день>&view=attention` | главный сценарий «где проблема» |
| KPI «На паузе» | `#incidents?at=<день>&view=paused` | объясняет зависшие обращения |
| KPI «Завершено за период» | **без перехода** (DEC-01) | поток за период не соответствует множеству строк |
| Строка «Ждут подтверждения» | `#incidents?at=<день>&view=review` | очередь решения контролёра |
| Элемент разреза по подразделениям | `#incidents?at=<день>&department=<id>` | обращения подразделения |
| «Все обращения →» в панели «Требуют внимания» | `#incidents?at=<день>&view=attention` | сохраняет контекст панели |
| «Все обращения →» в тулбаре | `#incidents?at=<день>` | общий список без фильтров |

- **Требование:** переход сохраняет `at` и контекстные фильтры; после перехода пользователь видит ровно тот набор, который образовал показатель (критерий проверяется тестом на равенство множеств).
- **Требование:** KPI с переходом — настоящий `<a href>` (клавиатура, копирование ссылки, back/forward), без JS-навигации.
- **Запрещено:** делать кликабельными показатели, для которых нет однозначного множества строк (DEC-01), и создавать новые параметры URL — контракт UX-3.2.1 уже содержит `view`, `department`, `at` (FACT).

### FR-03. Историческая семантика KPI

- **Требование:** все KPI Dashboard остаются историческими (по дате среза); формула `attention` остаётся доменной (`needsAttention`), дублирование в UI запрещено. FACT: сейчас условие выполнено.
- **Требование:** отсутствие данных не подменяется нулём: «Нет данных» для показателей, которые нельзя посчитать (существующее поведение).
- **Запрещено:** вводить накопительные (за период) значения в карточки мгновенного состояния и наоборот (DEC-01).

## 3. DEC-03 — варианты и рекомендация

| Критерий | A: текущая очередь | B: историческая очередь | C: разделённая семантика |
|---|---|---|---|
| Смысл счётчика | ожидают подтверждения **сейчас** | ожидали подтверждения **на выбранную дату** | сейчас + отдельное историческое значение |
| Соответствие дашборду | нарушает «всё на дату» | согласовано с остальными KPI | согласовано, но два значения рядом |
| Совпадение счётчика и списка | **не выполняется** (3 дня из 25, FACT) | выполняется по построению | выполняется для обоих значений |
| Сложность | минимум | минимум (одна строка + тесты) | выше: два значения, подписи, правило показа |
| Требования к данным | текущий статус | `lifecycleStatusOn` (есть) | оба |
| URL | без изменений | без изменений | без изменений |
| Влияние на переходы | ссылка ведёт в список, который не равен счётчику | ссылка и счётчик совпадают | нужны два перехода |
| UX-риск | пользователь видит «6», а в списке 5 строк | исторический счётчик может не отвечать на вопрос «что ждёт меня сейчас» | перегрузка панели |
| Ограничения данных | — | у обращений без lifecycle статуса нет | — |

**Рекомендация (INFERENCE, не решение):** вариант **B** — он делает счётчик и список одним утверждением, согласуется с уже принятой исторической семантикой KPI и не требует новых данных и параметров. Вариант **A** оставляет расхождение, вариант **C** добавляет информационный шум, не снимая вопроса «что показывает основной счётчик».

**DEC-03: PENDING OWNER DECISION.** Владельцу предлагается подтвердить вариант B (рекомендация) либо выбрать A или C. До решения реализация FR-01 не начинается; FR-02 (переходы) может быть реализован независимо, но ссылка «Ждут подтверждения» должна вести в `view=review` в любом варианте.

## 4. URL-контракт

Изменений не требуется: используются `at`, `view` (`active|attention|overdue|paused|review|unassigned`) и `department` (`DEP-*` | `none`) в существующей семантике UX-3.2.1 (`filtersHash`/`parseFilters` в `src/web/incidents.ts`). Legacy `review=pending` сохраняется только на чтение. Новых параметров не вводится.

## 5. Критерии приёмки (PASS/FAIL)

1. Для каждого дня окна модели число в счётчике «Ждут подтверждения» равно числу строк `#incidents?<день>&view=review` (проверка на 25 днях, включая 22.12, 23.12, 28.12).
2. Клик по KPI «Требуют внимания» открывает реестр, множество строк которого совпадает с `snapshot.attention` на ту же дату.
3. То же для «Активные обращения» (`snapshot.active`), «На паузе» (`snapshot.paused`).
4. KPI «Завершено за период» остаётся без перехода.
5. Строка «Ждут подтверждения» открывает `view=review`; счётчик и список совпадают.
6. Элемент разреза по подразделению открывает `department=<id>`; множество строк совпадает с `accountableOf` на дату.
7. Переходы — `<a href>`, доступны с клавиатуры; адрес воспроизводится после reload и по скопированной ссылке.
8. После перехода пользователь может определить причину попадания (виден активный фильтр в адресе; для `view`/`department` — после UX-3.2.4 в UI, до него — в адресе).
9. Даты вне окна модели дают единое состояние UX-3.2.2 без счётчика и без ссылок в пустоту.
10. Существующие unit- и e2e-наборы проходят без ослабления проверок.

## 6. Тестовая стратегия

- **Unit:** равенство счётчика и `snapshot.pendingReview` на всех днях окна (фикстура демо-истории + `tests/lifecycle-fixture.ts`); ссылки KPI содержат ожидаемые параметры; `view=review` равен `snapshot.pendingReview`; отсутствие перехода у «Завершено за период»; сохранение `at` в ссылках.
- **E2E:** клик по каждой KPI-ссылке → реестр с ожидаемым множеством строк (сравнение с числом из карточки); клик по «Ждут подтверждения» → счётчик равен числу строк; разрез подразделения; reload и back/forward после перехода; состояние вне окна.
- **Регрессия:** `tests/kpi-*.test.ts`, `tests/incidents-view-filters.test.ts`, `e2e/ux32.spec.ts`, `e2e/ux322.spec.ts`, `e2e/ux4.spec.ts`, `e2e/dashboard.spec.ts`, `e2e/ux-periods.spec.ts` — без изменений ожиданий (кроме случаев, где ожидание кодировало расхождение счётчика).

## 8. Риски и открытые вопросы

1. **DEC-03 — PENDING OWNER DECISION** (вариант B рекомендован).
2. Изменение видимого значения счётчика (на 22.12 1→2, на 23.12 2→1, на 28.12 4→3) — продуктовое изменение, требует фиксации в отчёте этапа.
3. Отсутствие UI-контролов `view`/`department` (UX-3.2.4): после перехода фильтр виден только в адресе — явно указать это в отчёте, не расширять scope.
4. Атрибуция подразделения исторически не разрешена (F5): переход `department` показывает текущее распределение; при необходимости исторической атрибуции требуется изменение модели назначений — отдельное решение.
5. **UNKNOWN:** нужен ли отдельный показатель «обращения без ответственного» на обзор — вне текущего scope.
