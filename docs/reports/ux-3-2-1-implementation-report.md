## 4. Реализованный URL-контракт

| Параметр | Допустимые значения | Валидация | Некорректное значение |
|---|---|---|---|
| `at` | `YYYY-MM-DD` | формат (существующее поведение экрана) | берётся последний доступный день |
| `view` | `all` / `active` / `attention` / `overdue` / `paused` / `review` / `unassigned` | белый список VIEWS | игнорируется → `all` |
| `review` (legacy) | `pending` | **только чтение** | игнорируется |
| `department` | `DEP-*` / `none` | регэксп `^(?:none|DEP-[A-Za-z0-9_-]+)$`, на уровне фильтра — проверка справочника | игнорируется → показываются все |
| `q`, `priority`, `sla`, `node`, `sort` | как раньше | существующие белые списки | игнорируются |

`filtersHash` формирует `q`, `priority`, `sla`, `node`, `sort`, `view`, `department`, `at` и **никогда** не пишет `review`. `view` и `sla` сочетаются; round-trip `filtersHash` → `parseFilters` возвращает исходный набор.

## 6. Обработка legacy alias (DEC-02)

1. `parseFilters` принимает `review=pending` и возвращает `view: review`; канонический `view` при наличии имеет приоритет.
2. `filtersHash` не формирует `review` ни при каких условиях — второго источника состояния нет.
3. Селект «Подтверждение» управляет `view`: выбор «ждут подтверждения» пишет в адрес `view=review`.
4. Старые ссылки продолжают открывать ту же выборку — проверено unit-тестом U2, e2e-сценарием B и браузерной проверкой.
5. Удаление алиаса — отдельное решение после этапа (как указано в спецификации).

## 7. Восстановление состояния фильтров

- `mountIncidents` читает состояние из `parseFilters(location.hash)` при каждом монтировании: URL — источник восстановления, а не отражение интерфейса.
- Дискретные изменения (приоритет, SLA, узел, сортировка, подтверждение, дата, сброс) пишутся в историю через `history.pushState`.
- Ввод поиска пишется через `history.replaceState`: иначе каждое нажатие клавиши создавало бы запись истории.
- Роутер слушает `hashchange` (`src/web/router.ts:90`) и перемонтирует экран, поэтому back/forward восстанавливают состояние фильтров из URL.
- Смена дня перерисовывает экран целиком и сохраняет остальные фильтры; смена одного фильтра не теряет остальные (адрес формируется из полного набора).

## 8. Обработка некорректных параметров

| Случай | Поведение |
|---|---|
| Неизвестный `view` | игнорируется → `all` |
| Некорректный формат `department` | игнорируется → показываются все |
| Формат верный, id отсутствует в справочнике | фильтр не применяется (`departmentFilterActive`), показываются все |
| `sla`, `priority`, `sort` вне белых списков | игнорируются (как раньше) |
| Пустые значения и повторяющиеся параметры | `URLSearchParams` берёт первое значение, пустое → значение по умолчанию |
| Конфликт `view` и `review=pending` | приоритет у канонического `view` |

Исключений не возникает, экран не ломается, неконтролируемых переходов нет — подтверждено unit-тестом U5, e2e-сценарием H и браузерной проверкой.

## 16. Известные ограничения

1. **UI-контролов для `view` и `department` нет** — они относятся к UX-3.2.3/3.2.4; контракт уже поддерживает оба параметра (задаются ссылкой, состояние восстанавливается и сохраняется, проверено сценариями A–F).
2. **Счётчик очереди на обзоре** по-прежнему считает текущий статус (`waitingForReview`, `src/web/org-integration.ts:85`): исправление входит в UX-3.2.3 (DEC-03), поэтому проверка «счётчик = очередь» в этом этапе сознательно не реализуется и не проверяется.
3. **Даты вне окна модели** обрабатываются как прежде (обзор и реестр — пустое состояние): единое состояние `outside_model_window` относится к UX-3.2.5.
4. **Неизвестные query-параметры** не переносятся в новые URL: `filtersHash` сериализует только известный набор. На маршруте реестра других параметров нет, потери состояния не возникает; при появлении новых их нужно добавить в контракт.
5. `accountableOf` возвращает `undefined` для обращений без ответственного (тип объявляет это явно); фильтр `department=none` учитывает оба пустых значения через `?? null`.
6. Сгенерированный `demo/app.js` после этого этапа снова отличается от исходников: при публикации UX-3.2.1 потребуется пересборка артефакта (как в RELEASE-3.2.1).
