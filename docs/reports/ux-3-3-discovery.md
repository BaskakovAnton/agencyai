## 5. Историческая атрибуция подразделений — F5 (FACT)

Модель данных содержит всё необходимое для исторической атрибуции:

- назначения имеют интервал: assignedAt, endedAt, departmentId, employeeId, assignmentType, status, reason, result (src/data/org-repository.ts, тип IncidentAssignment);
- в демо-данных **7 завершённых ответственностей** (передачи между подразделениями) с причинами и результатами, например endedAt 2025-12-22T04:00:00Z, reason «Демо-переназначение по нагрузке», result «Передано подразделению DEP-CONTROL»;
- подразделения: DEP-DISPATCH, DEP-HOUSING, DEP-ROADS, DEP-LIGHT, DEP-CONTROL, DEP-ARCHIVE;
- у обращения есть история перемещений по узлам (history: step/from/to/actor/note/at), но **связи узел→подразделение нет** (роли узлов не заполнены) — значит подразделение выводится только из назначений;
- у части обращений жизненный цикл пуст (records: 0), что уже влияет на очередь подтверждений.

**INFERENCE:** историческая атрибуция реализуема без изменения доменной модели: «подразделение на дату at» = активное на эту дату назначение типа accountable (интервал assignedAt ≤ at < endedAt), иначе последнее назначение, начавшееся до at. Требует продуктового подтверждения семантики (что считать ответственным за день, если передача произошла внутри дня) и покрытия тестами на 7 существующих передачах.

**UNKNOWN:** есть ли у назначений связь с жизненным циклом (кто инициировал передачу) и должна ли карточка показывать автора передачи — требует решения владельца.

## 12. Архитектурные ограничения и проблемы данных

1. **FACT:** атрибуция подразделения берётся из текущего активного назначения (accountableOf) — историческая атрибуция возможна, но не реализована (см. §5).
2. **FACT:** у части обращений нет записей жизненного цикла — очередь подтверждений и статусы для них неопределимы (ограничение UX-3.1).
3. **FACT:** нет связи узел→подразделение; передачи между подразделениями существуют только в назначениях.
4. **INFERENCE:** серверной части нет, все данные детерминированы генератором (buildStory) — «загрузка» и «ошибка сети» как состояния не существуют.
5. **UNKNOWN:** требуются ли в карточке вложения/документы (в модели их нет).

## 15. Итог Discovery

Продукт функционально согласован: фильтры, реестр, карточка, обзор и исторические состояния работают по единому контракту, регрессий предыдущих решений нет. Критические UX-проблемы сосредоточены в трёх местах: мобильный реестр (M-1), интерактивные зоны хронологии (M-2) и отсутствие читаемой истории передач в карточке при наличии данных (C-1). Историческая атрибуция подразделений (F5) технически возможна на существующих данных и требует продуктового решения.

Реализация не начиналась: спецификация, дизайн, код, тесты, CSS и demo не изменялись. Для перехода к Этапу 2 (SPECIFICATION) требуется решение владельца по трём пунктам: семантика исторической атрибуции, состав мобильного представления реестра (какие поля обязательны), и объём работ с Design System.
