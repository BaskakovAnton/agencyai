## 2. Границы периодов (решение)

- Период измеряется **в модельных календарных днях (UTC)**, как и весь проект; локальная тайм-зона браузера на расчёт не влияет.
- `period(N, endDay)` = дни `[endDay − (N−1) … endDay]`, обе границы включительно.
- `previous(period)` = дни `[endDay − (2N−1) … endDay − N]` — той же длины, вплотную, **без пересечения**.
- Конец периода — выбранная дата среза `?at=`; данные после неё скрыты (`visibleAt`), поэтому «незавершённого» периода в демо нет: любой выбранный день считается полным на дату.
- Значения по умолчанию: `N = 7`, `endDay` = последний день истории.
- Сравнение Snapshot: значение на конец текущего периода против значения на конец предыдущего периода (день перед началом текущего).
- Сравнение Flow: события внутри текущего периода против событий внутри предыдущего.
- Проценты: `(current − previous) / previous`; если предыдущее значение 0 — вместо процента выводится «—», а при обоих нулях «Нет данных».

## 3. Реестр показателей

| Название | Тип | Формула | Источник | Сравнение | Смысл роста |
|---|---|---|---|---|---|
| Активные обращения | Snapshot | `visible(day) − finished(day)` | timeline + isFinished | конец текущего vs конец предыдущего периода | нейтральный |
| Просроченные | Snapshot | число заявок с `slaPhaseOnDay = overdue` | sla-at | как выше | хуже |
| На паузе | Snapshot | число заявок с `slaPhaseOnDay = paused` | sla-at | как выше | нейтральный |
| Ждут подтверждения | Snapshot | число заявок со статусом жизненного цикла `pending_review` на дату | org/completion (журнал записей) | как выше | хуже |
| Поступило | Flow | заявки с `createdAt` внутри периода | timeline | текущий vs предыдущий период | нейтральный (объём) |
| Завершено | Flow | заявки, впервые достигшие терминального узла внутри периода | история переходов + isFinished | то же | лучше |
| Переоткрыто | Flow | записи `reopened` с `at` внутри периода | org/completion | то же | хуже |
| Подтверждено контролёром | Flow | записи `approved` внутри периода | org/completion | то же | лучше |
| Отказано в подтверждении | Flow | записи `rejected` внутри периода | org/completion | то же | хуже |
| Назначено подразделений | Flow | назначения с `assignedAt` внутри периода | org/assignments | то же | нейтральный |
| Изменение остатка | Дельта | `active(конец) − active(день до начала)` | timeline + isFinished | не сравнивается (сама дельта) | хуже при росте |
| Доля завершённых в срок | Эффективность | завершённые в периоде без `breached` на момент завершения / все завершённые в периоде | sla-at + история | текущий vs предыдущий период | лучше |

**Ограничения достоверности:**
1. Участие сотрудников по времени не детализировано — считаются назначения подразделений, а не человеко-часы.
2. Атрибуция просрочки конкретному подразделению некорректна (ответственный меняется, причина просрочки не структурирована) → **рейтинг подразделений по SLA не строится**; доступны только счётчики назначений и завершений по ответственному на момент решения.
3. Часть записей подтверждения демо-истории может быть датирована позже последнего дня среза — такие записи в периоды не попадают (это честно фиксируется счётчиком и примечанием).
4. Показатели «время в статусе» и «средняя длительность» не считаются: статусы пауз не имеют парных меток начала/конца в модели.

## 9. Что не реализовано и почему (NOT_IMPLEMENTED)

1. **Рейтинг подразделений по эффективности** — атрибуция просрочки к подразделению недостоверна:
   ответственный меняется, причины паузы не структурированы, «время в статусе» не имеет парных меток.
   Вместо рейтинга — счётчики назначений/завершений и разрез по ответственному на момент решения.
2. **Графики сверх панели «Динамика за период»** (стеки, тренды, прогнозы) — не помогают принять решение
   и не определены в утверждённом макете; сделана только честная дневная динамика.
3. **Средняя длительность и время в статусе** — модель не хранит парные метки входа/выхода, кроме узлов.
4. **Отдельные экраны периодной аналитики** — задача ограничена Dashboard.
