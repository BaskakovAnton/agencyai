## 5. Известные ограничения (честно)

1. **Аутентификации нет:** `actorUserId` — параметр операции; проверяются только полномочия из членств, личность доверяется границе домена.
2. **Личность исполнителя проверяется косвенно:** `submitExecution` требует, чтобы у обращения был назначенный сотрудник (или право `incident.participate`), но не сверяет актора с конкретным `employeeId` — для строгой проверки нужна связка User→Employee у обращения.
3. **Права — плоский список** `Permission`; ролей и RBAC нет.
4. **UI не подключён:** новые данные не отображаются (по условию задачи UI не делаем).
5. **`Incident` не расширен:** назначения живут отдельным набором; старые экраны подразделений не видят.
6. **`PriorityChanged`, `DeadlineChanged`, `IncidentCreated`** объявлены в типах; операции для первых двух — задача UX-3, `IncidentCreated` можно эмитить при подключении генератора к орг-истории.
7. **Storage/API отсутствуют** по ограничениям §10; история живёт в памяти прогона.
8. **Дедупликации событий при повторном прогоне нет** — id детерминированные, но история пересобирается с нуля.

## 6. Что осталось для UX-3

1. Repository-интерфейсы (по условию — отдельная задача) и адаптеры под будущее хранение.
2. Перенос назначений в `Incident` либо отдельный агрегат с версионированием.
3. RBAC: роли вместо плоского списка прав; `submitExecution` — сверка актора с исполнителем.
4. UI: разрез Dashboard по подразделениям, карточка обращений с ответственными, экран контроля подтверждения.
5. События `PriorityChanged`/`DeadlineChanged` + журнал аудита на чтение.

**Готовность к следующему этапу:** доменная модель, операции и проверки готовы и не ломают существующий продукт; для UX-3 можно начинать с Repository-интерфейсов и подключения к SPA.
